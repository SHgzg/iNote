# Nacos 基础：服务注册发现与配置中心

Nacos 可以先从两个核心能力理解：**Naming（服务注册与发现）**和 **Config（配置管理）**。前者解决微服务实例地址动态变化的问题，后者解决配置分散和环境差异的问题。

## 一、为什么微服务需要服务注册与发现

单体或固定部署时，服务之间可以直接使用固定地址。例如 `order-service` 直接请求某个 `user-service` 的 IP 和端口。

进入微服务后，一个逻辑服务通常存在多个实例：

```text
user-service
├── 10.0.0.11:8080
├── 10.0.0.12:8080
└── 10.0.0.13:8080
```

这些实例还会不断启动、停止、扩容、缩容、故障或迁移。消费者如果直接保存实例 IP，就需要自己追踪这些变化。

Nacos 在这里充当服务目录。服务实例启动后向 Nacos 声明自己的服务名和地址，这就是**服务注册**；消费者需要调用某个服务时，根据服务名获取当前可用实例，这就是**服务发现**。

基本关系是：

```text
服务提供者
    ↓ 注册
Nacos Registry
    ↑ 查询
服务消费者
```

消费者因此只需要认识 `user-service` 这样的逻辑服务名，而不需要长期绑定某个具体 IP。

## 二、Nacos 不负责业务流量转发

服务发现不能理解成业务请求经过 Nacos 转发。典型过程是：

```text
① user-service → Nacos
   注册实例地址

② order-service → Nacos
   获取 user-service 的实例列表

③ order-service ─────→ user-service
             HTTP / RPC
```

Nacos 的职责是回答“服务在哪里”，真正的业务请求由消费者直接发送给目标服务实例。

这与 Nginx、Gateway 等流量入口的职责不同：

```text
Nacos
→ 服务发现
→ 提供服务及实例信息

Nginx / Gateway
→ 流量转发
→ 接收请求并决定转发目标
```

## 三、为什么注册中心还需要健康状态维护

只有地址列表还不够。某个已经注册的实例可能随后崩溃，例如：

```text
10.0.0.11:8080   正常
10.0.0.12:8080   正常
10.0.0.13:8080   已故障
```

如果注册中心仍把第三个实例当成正常节点，消费者就可能继续请求它。因此 Nacos 还需要维护实例的健康状态，让消费者能够获得当前可用的实例。

服务注册发现的整体链路可以概括为：

```text
服务实例启动
      ↓
注册到 Nacos
      ↓
Nacos 维护实例列表
      ↓
维护实例健康状态
      ↓
消费者发现服务
      ↓
获得健康实例
      ↓
负载均衡选择实例
      ↓
直接调用目标服务
```

## 四、为什么还需要配置中心

微服务系统通常同时存在多个服务和多个环境。数据库、Redis、日志级别以及业务参数等配置如果分别保存在各个应用内部，会逐渐形成大量分散配置：

```text
开发环境配置
测试环境配置
生产环境配置
不同服务配置
不同服务器配置
```

Nacos Config 提供集中配置管理：

```text
              Nacos Config
                   │
        ┌──────────┼──────────┐
        ↓          ↓          ↓
      user       order      payment
    service     service     service
```

服务可以从 Nacos 获取自己的配置，并监听配置变化。这样配置管理就形成另一条链路：

```text
集中存储配置
      ↓
服务获取配置
      ↓
区分服务和环境
      ↓
配置发生变化
      ↓
服务感知变化并更新相应配置
```

## 五、Nacos 的整体心智模型

可以把 Nacos 看成两套能力组合在一起：

```text
                    Nacos
                      │
          ┌───────────┴───────────┐
          │                       │
    Naming Service          Config Service
      服务目录                 配置仓库
          │                       │
          ↓                       ↓
 user-service                 database.url
 ├─ instance A               redis.host
 ├─ instance B               日志与业务配置
 └─ instance C
```

其中 Naming 侧重点是：

- 服务注册
- 服务发现
- 实例管理
- 健康状态维护

Config 侧重点是：

- 配置集中存储
- 配置获取
- 配置监听
- 动态更新

因此学习 Nacos 时，首先建立的核心判断是：

> Nacos 同时解决“服务在哪里”和“服务应该使用什么配置”两个问题；它本身通常不位于业务请求的数据转发链路中。
