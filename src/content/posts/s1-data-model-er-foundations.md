# S1 数据模型与 ER 图基础：实体、标识符、约束与关系基数

这一阶段完成了 S1 的两个基础模块：

1. 实体、属性、标识符、关系与约束；
2. 关系基数、最小基数与可选性。

当前还没有完成整个 S1。后续仍需学习 M:N 关系拆解、关联实体、ER 图表示、弱实体以及泛化与继承。

## 一、建模不是直接建表

数据建模要先描述业务事实，再决定数据库如何实现。三个层次依次是：

| 层次 | 主要问题 | 典型产物 |
| --- | --- | --- |
| 概念模型 | 业务中有哪些核心对象，它们如何联系 | 核心实体和关系 |
| 逻辑模型 | 对象有哪些属性、标识符、基数和约束 | 完整 ER 模型 |
| 物理模型 | 如何落实到特定数据库 | 表、字段、主键、外键、索引、约束 |

容易犯的错误是过早把外键字段当成业务概念本身。例如，“设备属于用户”首先是一条逻辑关系；到了物理模型中，它才通常表现为：

```text
devices.user_id → users.id
```

因此，逻辑关系不等于物理外键。大型分布式系统即使没有建立数据库外键，逻辑关系仍然存在，也仍需维护引用完整性。

## 二、实体、属性、标识符、关系与约束

### 1. 实体

实体是需要独立识别、持续管理，并拥有自身生命周期的业务对象。

判断一个概念是否应成为实体，不能只看它是否重要，而要看它是否需要：

- 独立身份；
- 自身属性；
- 独立关系；
- 独立生命周期。

在物联网案例中，用户、设备和测量记录都是实体。

### 2. 属性

属性是描述实体的事实。例如：

```text
设备
- 设备名称
- 序列号
```

一个属性可以很重要，也可以具有唯一性，但这不会自动使它成为实体。

### 3. 标识符

标识符用于唯一识别一个实体实例。一个实体可以有多个候选标识符，但要从中选定一个主标识符。

属性和标识符不是互斥分类：

```text
device_id
- 设备的内部主标识符
- 由当前系统控制
- 适合内部关联

serial_number
- 设备属性
- 能唯一识别设备时，也是候选标识符
- 服务于生产、追溯和售后等业务
```

因此，“序列号是设备属性”和“序列号是候选标识符”可以同时成立。

### 4. 关系

关系表达实体之间的业务联系。例如：

```text
用户拥有设备
设备产生测量记录
```

“所属用户”在逻辑模型中更适合表达为设备与用户之间的关系，而不是设备的普通描述性属性。类似地，测量记录应当关联设备，而不是把“设备序列号”重复当作测量记录自身的普通属性。

物理表通常保存稳定的 `device_id`。如果每条测量记录都冗余保存设备序列号，序列号一旦变化，就可能与设备表产生不一致。

### 5. 约束

约束规定哪些数据状态和业务变化是合法的。它不只包含字段类型或数据库约束语法，还包括：

- 唯一性；
- 必填与可缺失；
- 引用完整性；
- 关系的最小和最大基数；
- 跨属性规则；
- 时间排他规则；
- 状态转换规则。

建模时应先完整说清“什么必须成立”，再决定由数据库约束、事务、锁、状态机还是应用逻辑实现。

## 三、物联网案例的完整逻辑模型

业务规则是：一台设备属于一名用户；用户可以拥有多台设备；设备会产生测量记录；测量时间必须存在，温度和湿度可以缺失；设备序列号不能重复；同一设备在同一测量时间不能出现两条记录。

### 实体与属性

```text
用户
- user_id：主标识符
- 用户名
- 昵称

设备
- device_id：主标识符
- serial_number：设备属性、候选标识符
- 名称

测量记录
- measurement_id：主标识符
- measured_at：测量时间
- temperature：温度，可缺失
- humidity：湿度，可缺失
```

### 关系及基数

```text
对一个用户：设备数量为 0..N
对一台设备：所属用户数量为 1..1

对一台设备：测量记录数量为 0..N
对一条测量记录：所属设备数量为 1..1
```

关系类型可概括为：

```text
用户 1:N 设备
设备 1:N 测量记录
```

但仅写 `1:N` 只能说明最大基数，无法表达“是否必须参与”。

### 约束

- `user_id`、`device_id`、`measurement_id` 分别唯一且非空；
- 设备序列号唯一且非空；
- 每台设备必须属于且只属于一个用户；
- 每条测量记录必须属于且只属于一台设备；
- 被关联的用户和设备必须真实存在；
- 测量时间必须存在；
- 温度和湿度允许缺失；
- 同一设备在同一测量时间最多只有一条测量记录。

最后一条可以表示为组合唯一约束：

```text
device_id + measured_at UNIQUE
```

`measurement_id` 唯一只能保证数据库记录的编号不同，不能阻止两条编号不同、业务含义却重复的记录。例如：

```text
记录 101：设备 A，10:00
记录 102：设备 A，10:00
```

两条记录的主标识符都唯一，但仍违反业务规则。主标识符唯一和业务事实唯一是两种不同约束。

## 四、关系基数必须从两端分别判断

每个关系端点都需要回答两个问题：

```text
最少关联多少个？
最多关联多少个？
```

常见表达如下：

| 表达 | 含义 |
| --- | --- |
| `0..1` | 可以没有，最多一个 |
| `1..1` | 必须有且只有一个 |
| `0..N` | 可以没有，也可以有多个 |
| `1..N` | 至少一个，可以有多个 |

最大基数决定关系是 1:1、1:N 还是 M:N；最小基数决定参与是可选还是强制。

识别时必须双向提问。例如“用户拥有设备”需要分别问：

1. 一个用户最少、最多拥有多少台设备？
2. 一台设备最少、最多属于多少个用户？

不能凭常识补充最小基数。需求只说“一个部门有多名员工”时，仍需确认新部门能否暂时没有员工，否则无法可靠判断是 `0..N` 还是 `1..N`。

## 五、历史记录数量不等于同时有效数量

图书馆案例中：

```text
对一册馆藏副本：历史借阅记录为 0..N
对一条借阅记录：馆藏副本为 1..1
```

这表示同一册副本在整个生命周期中可以被多次借阅，并不表示多次借阅可以同时有效。

还需要独立的时间排他约束：

> 任意时刻，一册馆藏副本最多只能存在一条“借出未归还”的有效借阅记录。

因此要区分：

- 关系基数：生命周期内可以产生多少条历史记录；
- 时间约束：同一时刻允许多少条有效记录。

“使用权具有排他性，不同时间可以由不同会员使用”的判断是正确的。这也说明借阅不是静态字段，而是有借出时间、归还时间和状态的借阅记录实体。

## 六、错题与反馈复盘

本阶段最重要的不是只记住正确答案，而是区分“真正答错”“答案不完整”和“原判断正确但反馈产生误解”。

### 1. 原本判断正确，不应记为错误

| 判断 | 结论 | 原因 |
| --- | --- | --- |
| 序列号是设备属性 | 正确 | 它描述设备的出厂身份 |
| 序列号也可唯一识别设备 | 正确 | 它可同时成为候选标识符 |
| 用户 1:N 设备 | 方向正确 | 表达了最大基数 |
| 设备 1:N 测量记录 | 方向正确 | 表达了历史记录数量 |
| 同一副本同一时间只能由一人使用 | 正确 | 正确识别了时间排他性 |
| `device_id + measured_at` 仍需唯一 | 正确 | 主键唯一不能代替业务唯一 |

关于序列号，曾经出现反馈表述不够准确的问题：原答案从未把序列号说成实体。真正需要修正的不是“序列号属于设备属性”，而是“测量记录也把设备序列号当作自身普通属性”。

### 2. 方向正确，但表达不完整

| 原表达 | 不完整之处 | 更严谨的表达 |
| --- | --- | --- |
| 设备可用序列号和 ID 标识 | 没有区分主标识符与候选标识符 | `device_id` 为主标识符，序列号为候选标识符 |
| 用户 1:N 设备 | 没有写最小基数 | 用户对应设备 `0..N`，设备对应用户 `1..1` |
| 设备 1:N 测量记录 | 没有写最小基数 | 设备对应记录 `0..N`，记录对应设备 `1..1` |
| 用户、设备、测量记录均具有唯一性 | 唯一性的对象不明确 | 各实体的主标识符唯一且非空 |
| 只列实体、属性和关系 | 漏掉题目要求的约束 | 继续提取唯一、必填、可空、引用和组合约束 |

这里的重点是：不完整不等于方向错误，但在正式建模中仍不能验收通过，因为缺失的信息会直接影响数据合法性。

### 3. 真正需要纠正的错误

#### 错误一：混淆逻辑关系与普通属性

原模型把“所属用户”列为设备属性，并把“测量设备的序列号”列为测量记录属性。

更准确的逻辑模型应表达为：

```text
用户 ——拥有—— 设备
设备 ——产生—— 测量记录
```

到了物理模型，关系才通常表现为 `device.user_id` 和 `measurement.device_id`。

#### 错误二：漏读“必须”，把 `1..1` 写成 `0..1`

题目明确说：

> 每条借阅记录必须对应一册馆藏副本。

因此一条借阅记录对应的馆藏副本数量必须是 `1..1`，不能是 `0..1`。

判断规则是：

- “必须”决定最小基数为 1；
- “一册”决定最大基数为 1。

#### 错误三：关系类型中混入了另一个实体

在判断“馆藏副本——借阅记录”时，关系类型被写成了“会员 1:N 馆藏副本”。这跨过当前关系，混入了另一实体。

关系类型必须严格沿用正在分析的两个端点：

```text
馆藏副本 1:N 借阅记录
```

不能因为借阅记录同时关联会员，就把三个实体压缩成一条未经定义的直接关系。

### 4. 当时没有主动完成的部分

约束清单最初没有完整作答，后来主要由反馈补全。这说明当前对实体和关系的识别已经较稳，但从业务句子中系统提取约束仍需刻意训练，尤其是：

- 哪些字段唯一、非空或可缺失；
- 哪些关系必须存在；
- 哪些规则是组合唯一；
- 哪些规则涉及时间区间或状态；
- 主键唯一是否真的保证了业务事实不重复。

## 七、当前可复用的建模检查顺序

面对新需求时，按以下顺序分析：

1. 找出需要独立识别和持续管理的实体；
2. 提取描述各实体的属性；
3. 为每个实体选择稳定的主标识符；
4. 找出其他候选标识符；
5. 用业务动词识别实体关系；
6. 从两个方向分别判断最小、最大基数；
7. 将 M:N 关系标记为待拆解对象；
8. 提取唯一、必填、可空、引用、组合、时间和状态约束；
9. 区分逻辑关系与物理外键；
10. 用具体合法和非法案例验证模型。

当前最需要强化的是第 6 步和第 8 步：读到“可以”“必须”“最多”“至少”“同一……不能重复”“同一时间”等词时，要立即把它们翻译成基数或约束。
