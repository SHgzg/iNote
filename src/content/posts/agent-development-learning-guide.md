# Agent 开发与应用学习指南：从任务价值到 Harness 与语言生态

## 一、学习目标：把局部智能转化为可验收的结果

Agent 开发与应用应围绕“任务价值—系统设计—执行可靠性—持续运营”建立完整视角。

模型提供理解、推断、生成与行动建议；工程系统负责信息、状态、行动接口、反馈、权限与资源边界。学习目标是让这些部分共同完成真实任务，而不是只掌握一种 SDK 或积累提示词。

这份指南既是一张学习地图，也是一份项目评审清单。主要面向已有软件工程经验、希望进入 AI Product Engineer 并逐步走向 AI Architect 的工程师。

需要持续追问：

1. 任务为什么值得自动化？
2. 哪些决策需要模型，哪些步骤适合确定性代码？
3. 模型每一步需要看到什么、能够做什么？
4. 系统如何证明有进展、已经完成？
5. 失败后如何恢复，什么时候应该停止？
6. 总成本、维护成本和业务收益是否匹配？

## 二、立项：判断什么任务值得交给 Agent

| 关注点 | 必须回答的问题 |
| --- | --- |
| 业务价值 | 帮谁完成什么工作？节省时间、减少错误，还是提供新能力？ |
| 任务适配性 | 是否需要根据中间结果动态选择步骤？固定代码或工作流能否更简单地完成？ |
| 任务边界 | 输入、输出、允许操作的对象、禁止事项是什么？ |
| 验收标准 | 什么叫完成？哪些条件可以通过程序、事实或人工检查？ |
| 失败代价 | 错误是否可发现、可撤销、可重做？哪些动作必须人工确认？ |
| 经济可行性 | 模型、基础设施、人工复核和失败返工的总成本是否合理？ |

立项时就定义验收和失败处理。演示成功只能说明任务在一次条件下被完成，不能自动证明长期稳定性。

架构上，模型可以处理理解与不确定决策；精确计算、业务约束、权限校验和已知流程应评估是否交给确定性代码。自主程度应由任务需要决定。

## 三、先区分关键概念

| 概念 | 主要职责 |
| --- | --- |
| Model | 根据输入产生推断、输出和行动建议 |
| Prompt Engineering | 表达目标、规则与输出要求 |
| Context Engineering | 决定当前一步向模型提供哪些信息 |
| 知识与 RAG | 从外部资料中检索当前需要的信息，并管理来源与时效 |
| Memory | 选择性保留过去的信息，供未来任务使用 |
| Tools / MCP 接口 | 提供访问数据和执行行动的通道 |
| Workflow / Orchestration | 安排步骤、分支、依赖、任务与协作关系 |
| Harness | 将模型、上下文、工具与约束接入执行循环，管理反馈、状态和停止条件 |
| Verification | 验证当前动作、阶段产物或最终交付物是否符合要求 |
| Evals | 使用任务集与评价方法检验系统能力、可靠性及退化情况 |

Harness 的边界尚不完全统一。较窄的口径指调用模型、路由工具与维持循环的运行时；较宽的口径还包括提示词、上下文管理、编排、Hooks、约束和执行环境。阅读文章或比较框架时，先确认其定义。

“评估 Harness”也可能专指测试与评分框架，不能只凭名称判断讨论范围。

## 四、开发时关注十三个系统维度

下面是用于组织学习和设计工作的工程分类，不是社区热度排名。

| 维度 | 主要设计内容 | 典型失败 |
| --- | --- | --- |
| 任务与规格 | 目标、约束、交付物、阶段、验收与需求变更 | 任务偏离；擅自扩大范围 |
| 模型选择 | 能力适配、工具调用、结构化输出、多模态、延迟与版本 | 只看总榜；更新后行为退化 |
| 架构与控制流 | 工作流与自主决策的分工；单 Agent、多 Agent；任务依赖 | 过度编排；拆分后无法整合 |
| 上下文工程 | 信息选择、检索、压缩、隔离、按需加载与来源标注 | 关键约束被淹没；压缩丢失事实 |
| 知识与记忆 | 权威性、时效、权限、溯源；记忆写入、更新与删除 | 推断固化成事实；过期知识影响决策 |
| 工具与行动 | 参数校验、明确反馈、超时、幂等、副作用与兼容性 | 重试导致重复提交；调用成功但业务未成功 |
| Harness 与运行时 | 执行循环、状态、预算、阶段门禁、恢复与终止 | 无效循环；过早结束；中断后丢失进展 |
| 验证与评估 | 结果验证、过程检查、代表性任务集与回归评估 | 自己生成并自行判定通过；只验证正常路径 |
| 安全与治理 | 身份、授权、租户隔离、沙箱、凭证、提示注入防护与审计 | 外部内容被当作指令；跨用户泄露 |
| 人机交互 | 进度、证据、预览、审批、纠错、取消与接管 | 用户不了解进展，也无法阻止执行 |
| 生产工程 | 队列、并发、持久化、故障恢复、发布与监控 | 重复执行；任务丢失；升级后无法追查 |
| 成本与性能 | 成功任务成本、耗时、模型路由、缓存、并行与重试预算 | 局部节省 Token，整体返工更贵 |
| 语言与生态 | SDK、依赖、运行环境、接口契约与维护成本 | 按语言偏好选架构；跨语言状态失控 |

这些维度需要联合设计。例如提交一份报告时，工具接口需要避免重复提交，Harness 需要记录状态，界面需要展示结果，验收需要检查内容与目标位置，权限系统需要限制提交范围。

多 Agent 也应视为一种架构选择。只有上下文隔离、独立验证或并行收益能覆盖通信与协调成本时，才值得引入。

## 五、Harness：让执行可以观测、验证、限制和恢复

### 1. 必要能力

| 能力 | 应落实的机制 |
| --- | --- |
| 明确目标 | 保存任务规格、验收条件和操作边界 |
| 组织输入 | 为当前步骤装配上下文，保留来源和关键约束 |
| 管理执行 | 调用模型与工具，记录结构化事件和结果 |
| 检查进展 | 判断是否获得新证据、消除阻塞或完成验收项 |
| 阶段验证 | 在关键节点执行程序检查、测试或人工复核 |
| 处理失败 | 区分可重试、需换策略和需人工处理的错误 |
| 持久化恢复 | 保存检查点；恢复时核对真实外部状态 |
| 控制终止 | 成功结束，或因预算、超时、无进展及风险退出 |

模型可以选择解决路径；权限、预算、超时、参数校验和关键验收应有可执行的程序约束。约束粒度需要通过任务验证：过细可能阻碍探索，过少可能造成越权与无效重试。

### 2. 区分活动、进展和完成

| 状态 | 判断依据 |
| --- | --- |
| 有活动 | 模型正在输出、工具正在调用 |
| 有进展 | 不确定性减少、阻塞被解除，或完成了可验收步骤 |
| 已完成 | 交付物满足验收要求，必要外部操作已确认生效 |

调用次数、输出长度和计划勾选不能单独证明进展。模型声称完成也不能替代真实证据。

对于 Coding Agent，需要检查代码是否满足需求、是否实际运行必要测试、测试是否有覆盖价值、最终运行状态是否正确。测试通过仍不自动等于全部需求满足。

### 3. 阶段检测与防循环

防循环应联合观察：

- 是否反复遇到同一错误；
- 是否重复相同操作却没有新证据；
- 环境或任务状态是否始终未变化；
- 验收项是否长期没有推进；
- 重试是否正在重复产生副作用；
- 时间与成本预算是否接近上限。

触发后可以重新检查假设、缩小问题、切换工具或策略、恢复检查点、重构上下文，必要时请求人工介入或明确停止。

恢复动作应与错误性质匹配：

| 情况 | 可考虑的处理 |
| --- | --- |
| 临时工具或网络故障 | 在预算与幂等条件允许时重试 |
| 当前产物不符合要求 | 修复产物并重新验证 |
| 原有路径反复失败 | 重新规划或切换方法 |
| 已造成错误外部变化 | 核对状态，评估撤销或人工处理 |
| 执行中断 | 从可靠检查点恢复，并确认外部状态 |
| 必要信息或授权缺失 | 请求人工补充或停止 |

具体阈值需要通过实际任务评估确定。要求“多反思几次”只能影响模型行为，不能替代外部检测和终止机制。

## 六、JS、TS、Python：按职责和依赖选择生态

### 1. 语言分工

JavaScript 是运行基础，TypeScript 提供开发期类型约束，两者通常属于同一套运行生态。Python 拓展了模型、数据处理与实验生态的接入范围。

对于已有 JS/TS 工程经验的开发者，可以优先用 TS 构建产品和 Agent 系统，同时掌握 Python，以便阅读、修改、复现实验并封装专项服务。这是一种学习路径建议，不是通用的语言优劣排序。

| 方向 | JS / TS 的切入点 | Python 的切入点 |
| --- | --- | --- |
| 产品交互 | 浏览器、Web、Electron、流式界面 | 接口服务或快速原型 |
| Agent / Harness | 应用服务、工具接口、任务状态与编排 | 模型、数据和实验流程的集成 |
| 模型调用 | 服务端调用与前后端流式传输 | 服务端调用与实验脚本 |
| 知识与 RAG | 业务系统连接、检索服务与交互 | 数据清洗、资料处理与检索实验 |
| 多模态 | 上传、预览、采集、编排与交付 | 文档、音视频和模型处理流程 |
| 训练与推理 | 调用端与应用集成 | 训练、微调、本地模型与 GPU 相关生态 |
| 评估 | 产品行为、工具接口和运行流程测试 | 批量实验、分析与研究复现 |

两种生态都能构建完整 Agent。不要把 TS 限定为前端，也不要把 Python 限定为模型训练。

### 2. SDK 与依赖选型检查

| 关注点 | 检查内容 |
| --- | --- |
| 功能完整性 | 工具调用、流式事件、结构化输出、追踪、会话与恢复 |
| 更新维护 | 新功能是否同步发布？文档、示例与版本是否一致？ |
| 扩展能力 | 能否控制上下文、替换模型、插入验证、修改重试和停止策略？ |
| 运行环境 | 浏览器、Node.js、桌面、容器或 GPU 环境的支持和限制 |
| 数据与工具依赖 | 所需解析器、数据库、浏览器和媒体处理库是否成熟？ |
| 评估与追踪 | 能否记录执行轨迹、回归测试并归因失败？ |
| 部署成本 | 安装体积、冷启动、内存、原生依赖、扩缩容与排障 |
| 迁移成本 | 业务规则和状态是否被框架绑定？更换模型与 SDK 有多难？ |

OpenAI SDK、Vercel AI SDK、LangGraph、Pi 等可以作为选型和源码学习对象，但功能与语言支持需要按具体版本核查。同一个框架提供 TS 和 Python SDK，不代表功能和维护节奏完全一致。

### 3. 跨语言边界

只有两端各自存在明确职责时，再拆分服务。跨语言系统重点处理：

| 问题 | 设计要求 |
| --- | --- |
| 数据契约 | 明确输入、输出和错误 Schema，两端执行运行时校验 |
| 类型差异 | 约定日期、时区、大整数、金额、二进制、缺失值和枚举 |
| 任务状态 | 使用统一任务 ID，明确状态保存者与完成判定者 |
| 超时与取消 | 用户取消后，后台处理是否同步停止？ |
| 重试与副作用 | 避免两端独立重试，造成重复写入、执行或计费 |
| 文件传递 | 大文件优先传受控引用，避免接口反复复制 |
| 追踪与审计 | 跨进程保留关联 ID，还原完整执行链 |
| 环境管理 | 锁定各自依赖，管理容器、原生库和 GPU 兼容性 |

TypeScript 类型不会自动校验运行时的外部数据，Python 类型标注也不会自动保证数据正确。接口必须有实际校验。

顶层任务状态、预算和退出策略应明确归属，避免两端各自循环、各自重试，却无人能解释任务为什么仍在运行。

## 七、应用与人机协作

| 环节 | 使用者与团队应关注的内容 |
| --- | --- |
| 委托前 | 提供目标、背景、资料来源、限制和验收标准 |
| 授权时 | 明确允许读取、修改、发送、发布的对象与范围 |
| 执行中 | 查看阶段成果和关键证据，及时纠正方向 |
| 验收时 | 核对制品、关键事实、测试、实际系统状态和副作用 |
| 失败后 | 保存失败案例与环境信息，判断该改指令、工具还是流程 |
| 长期使用 | 清理过期记忆、权限和集成，复查更新后的行为 |

重要任务应提前约定：什么时候自主继续，什么时候请求补充，什么时候必须停止并报告阻塞。

界面应让用户理解任务当前状态，能够预览重要结果、纠错、取消和接管。正确请求人工确认，在某些任务中就是成功行为，不能只追求无人干预率。

## 八、生产运营：用指标判断系统是否真的变好

| 指标 | 观察内容 |
| --- | --- |
| 验收成功率 | 交付物真正满足要求的比例 |
| 人工介入与返工量 | 每项任务需要多少纠正、复核与补做 |
| 每个成功任务的总成本 | 包含失败尝试、工具、基础设施与人工 |
| 完成时间 | 同时看典型任务和耗时最长的一部分任务 |
| 异常行动率 | 越权、重复副作用、错误写入等事件 |
| 恢复能力 | 中断、工具故障或限流后能否正确继续 |
| 回归情况 | 模型、提示词、工具和 Harness 更新后的变化 |

指标需要按任务类型、难度和风险分组。总体平均值可能掩盖某类任务持续失败。

应将真实失败案例纳入评估，兼顾最终结果与中间行为。模型升级、工具 Schema 变更、提示词修改和 Harness 调整，都可能改变整体表现。

## 九、工程师的学习顺序与阶段验收

学习顺序以端到端任务为主线，让每阶段形成可以检查的成果。

| 阶段 | 学习重点 | 阶段成果与验收问题 |
| --- | --- | --- |
| 1. 任务规格 | 价值、边界、验收、失败代价 | 有一份清晰规格；别人能否据此判断任务完成？ |
| 2. 最小闭环 | 模型调用、工具、结构化输出、交付 | 从输入到结果走通；是否核实工具执行和最终产物？ |
| 3. 评估与追踪 | 完整轨迹、失败归因、代表性任务 | 失败能否定位到模型、上下文、工具或环境？ |
| 4. Harness | 阶段门禁、进度、预算、退出、检查点 | 无进展能否停止？中断后能否正确恢复？ |
| 5. 信息系统 | 上下文、知识、RAG、记忆及权限 | 是否使用正确来源？能否处理过期、矛盾和无关信息？ |
| 6. 产品与生产 | 接管、审批、队列、并发、隔离、监控 | 用户能否控制执行？线上故障能否排查？ |
| 7. 架构优化 | 模型路由、缓存、并行、多 Agent | 是否用成功率、耗时和总成本证明优化收益？ |

JS/TS 工程师可以用熟悉的语言先完成闭环，再以具体依赖为牵引补 Python。Python 的阶段目标可以先定为：能读源码、修改示例、运行实验、处理数据并封装服务，再按需要深入训练与推理。

多 Agent 应在明确收益后引入，不作为入门的必经步骤。

## 十、贯穿实践：多模态资料整理与制品生成

一个适合作为学习主线的任务是：接收同一主题的多模态资料，整理内容，按目标生成可交付制品。

| 阶段 | 可检查的产物 | 验证重点 |
| --- | --- | --- |
| 接收资料 | 文件与来源记录 | 输入范围和权限是否清楚？ |
| 解析资料 | 带来源的文本与解析结果 | 是否遗漏或误读关键信息？ |
| 整理主题 | 结构、标签与内容草稿 | 是否保留事实、约束和未解决问题？ |
| 生成制品 | 文档、演示文稿或其他目标产物 | 是否满足目标格式与内容要求？ |
| 检查交付 | 内容和版式检查结果、最终制品 | 能否实际打开、检查并交付？ |

不同制品采用不同整理原则：详细文档侧重结构与完整性，演示文稿侧重重点与表达。不能只转换文件扩展名。

一个可采用的分工起点：

- TS：Web / Electron 界面、上传预览、流式进度、用户与权限、任务和元数据、顶层 Harness。
- Python：在具体依赖具有优势时，封装文档解析、数据处理、模型实验或本地推理能力。
- 数据库、对象存储、队列与日志：按职责设计，避免与某一种语言绑定。

先完成一条可信的交付链，再根据失败证据补上下文、验证、恢复和性能优化。

## 十一、持续学习：从信息发现走向验证

信息来源可以分四类：

| 类型 | 入口 | 主要用途 |
| --- | --- | --- |
| 官方工程来源 | Anthropic Engineering、OpenAI Developer Blog、Google DeepMind | 确认模型、产品与工程实践的一手信息 |
| 专业分析与实验 | Latent Space、Simon Willison | 理解生态、使用方法与边界 |
| 开源与研究 | Hugging Face、OpenReview、ModelScope | 跟踪论文、模型、代码与社区反馈 |
| 宏观态势 | Stanford HAI / AI Index | 理解产业采用、技术与经济变化 |

官方信息最适合确认自身产品，架构建议仍应结合约束验证。社区热度、论文结果和生产可靠性应分别判断。

可采用的节奏是：每日发现变化，每周精读并做小实验，每月回看趋势与学习方向。每次阅读至少留下五个答案：

1. 它解决了什么原始问题？
2. 机制为什么可能有效，依赖哪些条件？
3. 证据来自基准、实验还是生产实践？
4. 对当前语言栈和项目有什么影响？
5. 如何用一个小实验验证，而不是直接照搬？

## 十二、项目评审清单

- 任务价值、边界和验收是否明确？
- 是否需要 Agent，以及这种程度的自主性？
- 上下文是否保留来源、时效和关键约束？
- 工具是否有校验、明确反馈与副作用控制？
- 能否区分活动、进展和完成？
- 是否存在阶段验证、无进展处理和确定的退出条件？
- 中断后能否核对外部状态并恢复？
- 身份、权限、凭证和执行环境是否受到约束？
- 用户能否预览、取消、纠错和接管？
- 是否有完整轨迹、真实失败案例和回归评估？
- 是否统计成功任务总成本与人工返工？
- 语言与 SDK 选择是否有依赖和维护依据？
- 跨语言系统的状态、重试和退出权是否明确？
- 引入复杂度是否有可测量的收益？
