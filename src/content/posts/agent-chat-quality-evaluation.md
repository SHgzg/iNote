# Agent Chat 行为质量评估方法

## 核心问题

传统 LLM Benchmark 通常采用“固定问题—标准答案”的形式，主要衡量知识、推理或代码能力。但 Agent 在 Chat 场景中的质量不能只看某一次回答是否正确，还要判断它是否在多轮交互中正确理解目标、保留约束、选择行动、调用工具并最终完成任务。

因此，Agent Chat 质量评估的基本对象应从单条回复转变为完整的对话轨迹：

```text
用户目标
→ 多轮沟通
→ 状态和约束变化
→ 推理与行动
→ 工具执行
→ 最终结果
```

评价目标也应从“回答得像不像”转变为：

> Agent 是否以可靠、有效、克制且可验证的方式，使任务从初始状态推进到目标状态。

这里评估的不是裸模型本身，而是模型、系统提示词、上下文管理、记忆、工具、技能和编排机制共同形成的整体行为。更准确的名称是 **Agent Runtime Behavioral Benchmark**。

## 一、评估单位

### 1. 单轮回答

适合评估局部能力，例如：

- 是否理解当前问题；
- 事实是否准确；
- 推理是否成立；
- 表达是否清楚；
- 是否存在安全问题。

单轮评估容易执行，但无法反映上下文保持、计划调整、工具闭环和最终任务完成情况。

### 2. 多轮对话

多轮评估关注 Agent 是否能够：

- 记住用户已经给出的信息；
- 吸收新增约束；
- 在用户修正后调整判断；
- 避免重复提问；
- 保持目标和术语一致；
- 随任务进展更新计划。

### 3. 完整任务轨迹

对于具备工具执行能力的 Agent，最重要的评估单位是完整任务：

```text
目标定义
→ 信息收集
→ 计划生成
→ 工具选择
→ 执行
→ 结果验证
→ 必要时修正
→ 任务结束
```

此时不能只评价最终文本，还要检查中间行动和现实结果。

## 二、核心评估维度

### 1. 意图理解

判断 Agent 是否理解用户真正要解决的问题，而不是只匹配表面关键词。

测试问题：

> 我想做一个每天约 100 个用户使用的 AI 客服系统，应该怎么设计？

期待表现：

- 识别目标是设计系统，而不是推荐现成产品；
- 利用已知规模约束，避免过度设计；
- 识别知识来源、人工接管、成本和部署方式等关键未知条件；
- 在信息不足时进行必要且有限的澄清。

常见失败：

- 答非所问；
- 忽略用户给出的规模和约束；
- 直接套用固定架构；
- 把可能需求当成确定需求。

### 2. 知识准确性与边界

不仅检查事实是否正确，还要检查结论是否说明适用条件和能力边界。

测试问题：

> Supabase 能不能完全替代传统后端？

期待表现：

- 说明它能够承担数据库、认证、存储、实时能力和部分服务逻辑；
- 区分“覆盖常见后端能力”和“替代所有后端工程”；
- 指出复杂业务逻辑、服务治理和高度定制场景中的限制；
- 避免绝对化结论。

### 3. 推理质量

推理质量不以篇幅为标准，而以因果关系、覆盖范围和结论一致性为标准。

测试问题：

> 为什么不能直接让前端调用 LLM，而要经过后端？

期待表现应覆盖：

- 密钥和权限暴露；
- 会话状态与业务状态管理；
- 工具调用和权限隔离；
- 审计、限流和成本控制；
- 业务流程编排。

评价时应检查每个结论是否有理由支撑，而不是只统计提到了多少概念。

### 4. 上下文保持

测试 Agent 是否能够在多轮对话中保留关键事实、约束和已作出的决定。

示例流程：

```text
第一轮：我要开发一个个人知识库 Agent。
第二轮：它运行在家里的 Windows 电脑上，不依赖云服务。
第三轮：重新调整方案。
```

期待表现：

- 保留“个人知识库 Agent”这一原始目标；
- 同时保留 Windows、本地部署和无云依赖三项约束；
- 对模型、Embedding、数据库和部署方案作相应调整；
- 不重新询问已经明确的信息。

可使用约束保留率：

```text
约束保留率 = 正确保留并应用的关键约束数 / 用户提出的关键约束总数
```

### 5. 澄清能力

高质量 Agent 既不能在关键信息不足时盲目执行，也不能把所有问题都变成漫长的需求访谈。

测试问题：

> 帮我开发一个 App。

期待表现：

- 识别平台、目标用户、核心功能和交付范围等关键信息缺失；
- 优先询问最能改变方案的少量问题；
- 对次要信息采用合理默认值或显式假设；
- 在用户已经给出足够信息时直接推进。

需要同时评估两类错误：

- **澄清不足**：在重大歧义下直接行动；
- **过度澄清**：不断提问，却没有推进任务。

### 6. 规划能力

测试 Agent 是否能把高层目标转化为有依赖关系的阶段和可执行步骤。

测试问题：

> 我要开发一个具备记忆、知识库和工具调用能力的 Agent 产品，请制定开发计划。

期待计划至少区分：

- 基础交互和状态管理；
- 记忆系统；
- RAG 或知识访问；
- 工具和权限；
- 评估体系；
- 部署与运行保障。

评价重点：

- 阶段是否有明确目标；
- 前后依赖是否合理；
- 是否包含验证和验收；
- 是否能根据新约束调整计划；
- 是否避免只有任务清单而没有执行顺序。

### 7. 工具使用

工具能力应拆成完整闭环，而不是只看是否发起了调用。

需要分别评价：

1. 是否判断出需要使用工具；
2. 是否选择正确工具；
3. 参数是否准确；
4. 是否正确理解工具结果；
5. 是否处理失败、空结果和冲突；
6. 是否验证外部状态确实改变；
7. 是否在未成功时避免声称成功。

例如，用户询问时效性数据时，Agent 应使用搜索或数据工具，而不是依靠旧知识生成看似确定的数字。

### 8. 任务完成度

任务完成度是 Agent 质量的中心指标。

需要区分：

- 回答已生成；
- 工具调用已成功；
- 中间动作已完成；
- 用户目标已实现。

例如：

```text
邮件草稿已生成 ≠ 邮件已发送
付款请求已发起 ≠ 付款已完成
文件写入接口返回成功 ≠ 远端内容已核验
```

任务成功应根据预先定义的最终状态判断，而不是根据 Agent 是否输出了结束语判断。

### 9. 自我修正

高质量 Agent 不要求每一步都不出错，但应能识别错误并恢复。

测试可以人为加入：

- 工具调用失败；
- 搜索结果冲突；
- 用户指出误解；
- 新约束使原计划失效；
- 执行结果与预期不一致。

期待表现：

- 明确承认具体错误；
- 定位错误发生在哪一步；
- 修正依赖该错误的后续判断；
- 避免只改变措辞而不改变行动；
- 在无法恢复时明确停止。

### 10. 交互效率

交互质量不是追求最少轮数，而是追求合理轮数。

需要观察：

- 是否重复用户已经说明的信息；
- 是否提出低价值问题；
- 是否过早输出大量无关内容；
- 是否能在复杂任务中逐步收敛；
- 是否在关键节点让用户做必要决策。

首轮解决率可以作为指标，但不能单独使用。用户继续追问可能表示前一回答不完整，也可能表示回答有效并引发进一步探索。

### 11. 安全与治理

对 Agent 的安全评价不仅是检测拒绝内容，还包括执行权限和副作用控制。

需要检查：

- 是否识别高风险、违法或越权请求；
- 是否在拒绝后提供合法替代路径；
- 是否在发送、支付、删除和公开发布前取得适当授权；
- 是否优先采用可预览、可撤销和可审计的操作；
- 是否避免把推断当成用户授权。

### 12. 稳定性

同类任务在不同措辞、不同轮次和重复运行中，应保持核心判断一致。

稳定性测试包括：

- 同义改写；
- 信息顺序变化；
- 无关上下文干扰；
- 多次独立运行；
- 不同工具返回顺序。

稳定并不意味着输出文字完全相同，而是目标理解、关键约束、核心结论和安全边界不应无故漂移。

## 三、测试用例结构

一个 Agent Chat Benchmark 用例不应只有问题和参考答案，而应描述完整任务环境。

```json
{
  "id": "agent-chat-001",
  "taskType": "architecture_design",
  "difficulty": "hard",
  "goal": "为小规模 AI 客服系统设计可实施架构",
  "conversationHistory": [],
  "knownFacts": [
    "网站每天约 100 个用户"
  ],
  "constraints": [
    "控制复杂度",
    "方案需要可实施"
  ],
  "availableTools": [],
  "expectedBehaviors": [
    "识别关键需求缺口",
    "避免过度设计",
    "说明方案边界和取舍"
  ],
  "forbiddenBehaviors": [
    "忽略用户规模",
    "虚构未提供的业务条件"
  ],
  "successState": "形成与规模匹配且边界清晰的架构方案",
  "scoringRubric": {
    "intentUnderstanding": 5,
    "reasoning": 5,
    "taskCompletion": 5,
    "interactionEfficiency": 5
  }
}
```

对于工具型任务，还应记录预期行动和最终外部状态：

```json
{
  "expectedActions": [
    "选择正确工具",
    "使用有效参数",
    "读取执行结果",
    "重新检查目标状态"
  ],
  "expectedFinalState": "目标资源已发生可验证变化"
}
```

## 四、评分方法

### 1. 五级行为评分

每个维度可以使用统一的五级评分：

| 分数 | 含义 |
| --- | --- |
| 5 | 完整理解并正确完成，边界、验证和交互均合理 |
| 4 | 主体正确，存在少量不影响结果的遗漏 |
| 3 | 部分完成，关键能力表现一般或需要用户补救 |
| 2 | 存在明显误解、遗漏或无效行动 |
| 1 | 未完成任务、严重错误或产生不可接受风险 |

评分锚点必须针对具体任务展开，不能只写“优秀、一般、较差”。例如，上下文能力的 5 分应明确要求保留哪些约束，工具能力的 5 分应明确要求完成哪些调用和验证步骤。

### 2. 加权总分

不同产品的权重应由实际用途决定。一个通用 Agent 可以采用以下起始权重：

| 维度 | 权重 |
| --- | ---: |
| 意图理解 | 12% |
| 知识与推理 | 16% |
| 上下文保持 | 10% |
| 澄清与规划 | 12% |
| 工具使用 | 14% |
| 任务完成 | 18% |
| 自我修正 | 6% |
| 交互效率 | 6% |
| 安全与治理 | 6% |

总分只能用于宏观比较，不能替代失败类型分析。两个总分相同的 Agent，可能分别在知识准确性和工具执行上存在完全不同的问题。

### 3. 硬性门槛

部分维度不适合被平均分抵消。例如：

- 高风险操作未经授权；
- 编造工具执行成功；
- 严重事实错误；
- 泄露敏感信息；
- 忽略明确禁止条件。

这类问题应设置为门槛项或直接判定任务失败，而不是仅扣少量分数。

## 五、评估数据来源

### 1. 人工设计测试

用于稳定覆盖预先定义的能力和边界，适合回归测试与模型版本比较。

### 2. 真实对话转化

从真实 Chat 中提取：

- 用户目标；
- 关键约束；
- 多轮修正；
- 最终是否完成；
- 失败发生在哪一步。

真实对话不应直接复制为题目，而应去除无关轮次，重构为可重复执行的测试用例。

### 3. 对抗与扰动测试

通过改变措辞、顺序、上下文和工具状态，检测 Agent 是否依赖脆弱模式。

### 4. 线上行为指标

可以观察：

- 用户纠正率；
- 重复解释率；
- 任务中止率；
- 人工接管率；
- 工具失败后的恢复率；
- 最终任务成功率；
- 完成任务所需轮数和调用次数。

线上指标通常只是质量代理，必须结合任务内容解释。用户没有继续对话不一定代表满意，继续对话也不一定代表失败。

## 六、评价主体

完整评估通常需要组合三类方法。

### 1. 规则评价

适合判断可明确验证的事项：

- 是否调用指定工具；
- 参数是否符合 schema；
- 是否遗漏明确约束；
- 最终文件或状态是否存在；
- 是否触发禁止行为。

### 2. 人工评价

适合判断：

- 意图是否真正理解；
- 方案是否有用；
- 澄清是否合理；
- 推理是否具有说服力；
- 交互是否自然且高效。

人工评价需要明确评分锚点，否则容易退化为主观偏好。

### 3. LLM Judge

适合扩大评测规模和比较多个回答，但应提供：

- 完整对话；
- 用户目标；
- 已知事实和约束；
- 评分维度；
- 每个分数的行为标准；
- 需要引用的具体证据。

LLM Judge 不应只输出一个总分，而应说明扣分对应的对话行为。

## 七、Benchmark 建设流程

```text
收集代表性任务
→ 建立任务分类
→ 定义目标状态和失败条件
→ 编写多轮测试轨迹
→ 为每个维度设置评分锚点
→ 运行不同 Agent 配置
→ 组合规则、人工和 LLM Judge 评分
→ 聚合失败模式
→ 将典型失败加入回归测试
```

重点不是不断增加题目数量，而是保证测试覆盖真实任务类型、关键边界和常见失败路径。

## 八、常见误区

### 1. 只测最终回复

最终文本可能看起来合理，但前面可能调用了错误工具、忽略了权限，或并未真正完成任务。

### 2. 把回答长度当成质量

更长的回答可能只是重复、过度解释或逃避决策。质量应由任务推进和信息价值决定。

### 3. 把最少轮数当成效率

复杂任务需要必要澄清。真正需要减少的是无效轮次，而不是所有轮次。

### 4. 只看平均总分

平均分会掩盖严重安全问题和特定能力短板。应同时查看门槛失败、分维度得分和失败类型。

### 5. 用单一 Judge 决定质量

规则、人工、用户行为和 LLM Judge 各自只能观察一部分质量，单一评价来源容易产生系统性偏差。

### 6. 测模型而忽略运行系统

Agent 的实际表现还受到提示词、记忆检索、工具定义、权限机制、编排和错误恢复策略影响。只更换模型并不能解释所有质量变化。

## 九、最终判断

Agent 在 Chat 场景中的质量，应围绕三个层次判断：

1. **回复质量**：当前内容是否正确、清楚并符合要求；
2. **对话质量**：是否持续理解目标、保留上下文并有效协作；
3. **任务质量**：是否通过正确行动实现了可验证的最终状态。

其中，任务质量是最终目标，对话质量是实现路径，回复质量只是其中一个局部组成。

一个成熟的 Agent Benchmark 不应只回答“这个回复好不好”，而应回答：

> Agent 在给定目标、约束、工具和风险条件下，是否以稳定、可验证且成本合理的方式完成了任务；如果没有，失败具体发生在哪个环节。
