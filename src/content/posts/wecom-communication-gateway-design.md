# 企业微信自建应用通信能力网关设计

## 一、系统定位

系统定位为**企业微信通信能力网关（Enterprise WeCom Communication Gateway）**，面向多个内部业务系统提供统一、标准化、可治理的通信与协作能力。

它不是独立的企业协作业务平台，也不是工单、故障、审批或项目管理系统。业务系统通过网关发起通信请求，网关负责调用企业微信、企业邮箱等外部渠道，管理通信请求和外部资源的技术状态，并将用户交互结果回调给业务系统。

核心闭环：

**业务系统发起请求 → 网关执行通信 → 用户接收并交互 → 网关记录事实 → 回调业务系统 → 业务系统裁决业务结果**

### 1.1 已确定的产品决策

| 维度 | 决策 |
| --- | --- |
| 平台定位 | API Gateway，主要向内部业务系统提供统一能力 |
| 邮件 | 同时支持企业微信邮箱和外部企业邮箱 |
| 表格 | 同时支持企业微信智能表格和内部表格 |
| 任务 | 优先使用企业微信原生待办，接口能力需验证 |
| 群聊 | 只支持业务触发的临时群，不管理固定部门群 |

### 1.2 网关与业务系统的职责边界

| 事项 | 网关职责 | 业务系统职责 |
| --- | --- | --- |
| 消息通知 | 发送消息、跟踪通信状态 | 决定通知原因、内容和对象 |
| 消息等级 | 执行等级对应的通信策略 | 定义业务等级和业务时限 |
| 确认交互 | 记录用户操作并回调 | 判断确认是否满足业务条件 |
| 超时提醒 | 按授权策略执行提醒 | 定义超时和升级规则 |
| 邮件 | 发送、接收及查询授权范围内的邮件 | 决定邮件业务内容 |
| 临时群 | 创建和管理网关有权管理的群 | 决定创建时机、群成员和用途 |
| 会议 | 创建、修改、取消和查询会议 | 决定会议目的和参会人员 |
| 待办 | 调用待办能力并同步可获得的状态 | 定义任务内容及业务完成条件 |
| 表格 | 执行授权的数据读写 | 定义数据的业务含义 |
| 最终业务状态 | 不作裁决 | 负责最终裁决 |

网关可以维护通信请求状态，但不能把通信状态冒充业务状态。例如，**Acknowledged** 只表示用户确认收到，不等于故障已认领、审批已通过或任务已完成。

## 二、总体架构

建议按统一 API、领域服务、通用治理能力和渠道适配器分层：

1. **内部业务系统**：故障治理、工单、审批、项目及其他内部系统。
2. **统一接入层**：REST API、SDK、调用方认证、API 版本管理。
3. **领域能力层**：消息通知、邮件、临时群聊、会议、日程、待办、文档表格、组织身份。
4. **通用治理层**：权限、限流、幂等、异步任务、回调、状态追踪、审计和监控。
5. **渠道适配层**：企业微信自建应用 API、企业微信邮箱、外部邮箱、内部表格服务及后续协作平台。

### 2.1 与企微机器人中心的关系

通信能力网关和智能机器人中心应保持独立：

- 通信网关面向多个业务系统，提供自建应用、邮件等通用通信能力。
- 机器人中心面向智能机器人 API 长连接及其交互能力。
- 两者可以复用内部身份中心和部分通信基础设施，但应用凭证、权限配置和故障隔离应独立。
- 不应把机器人中心改造成自建应用的子模块，也不应让两个系统共享不受限制的企业微信 Secret。

## 三、功能范围

### 3.1 消息与通知服务

消息服务支持个人、指定群和混合对象，消息形式包括文本、图文、模板卡片、文件等。具体类型以企业微信接口和权限验证结果为准。

核心能力：

- 个人消息、群消息和批量发送。
- 模板消息与模板卡片。
- 卡片按钮交互、卡片状态更新。
- 文件发送。
- 定时发送和超时提醒。
- 消息发送结果查询。
- 接收确认、接受、拒绝等交互事件。
- 交互记录查询和回调。
- 在渠道能力允许时执行撤回等操作。

#### 消息等级

等级是网关内部的标准化策略，不是企业微信原生消息等级。

| 等级 | 名称 | 建议默认策略 |
| --- | --- | --- |
| L0 | 普通 | 单次发送 |
| L1 | 重要 | 发送及发送状态跟踪 |
| L2 | 紧急 | 发送、确认及超时提醒 |
| L3 | 严重 | 多渠道触达、确认及升级 |

等级与交互要求分开建模。等级不能直接推导出必须确认；是否要求阅读、确认或接受处理，应由通知策略明确指定。

策略可包含：

- 是否要求阅读或确认。
- 确认规则：任意一人、全员、最少人数或指定人员。
- 截止时间、提醒间隔和最大提醒次数。
- 备用渠道及升级规则。
- 消息过期时间。
- 是否允许业务系统关闭跟踪。

#### 接收对象与响应对象

发送对象和响应对象是不同概念。向一个群发送通知，可以只要求指定负责人确认，不应默认要求所有群成员确认。

- 个人通知：一个或多个员工。
- 指定群通知：一个或多个已授权群。
- 混合通知：个人与群组同时发送。
- 响应对象：独立指定人员、角色或群成员范围。

#### 交互事实

至少区分以下状态和事件：

- 已提交：网关接受请求。
- 已发送：渠道接口返回相应成功结果。
- 已送达：渠道确实提供可验证的投递证据时记录。
- 已读：仅在存在真实、可靠的阅读证据时记录。
- 已确认：用户明确执行确认操作。
- 已接受：用户接受承担事项。
- 已拒绝：用户明确拒绝。
- 已过期：交互窗口或通知有效期结束。
- 已失效：业务规则或网关策略关闭原交互入口。

送达、已读、确认、接受和完成不能互相推断。尤其不能将发送成功当作已读，也不能将确认收到当作业务完成。

### 3.2 邮件服务

采用统一邮件领域接口和多个渠道适配器：

- 企业微信邮箱适配器。
- 外部企业邮箱适配器。

功能范围：

- 普通邮件和 HTML 邮件发送。
- 附件。
- To、CC、BCC。
- 多人发送。
- 邮件模板。
- 应用邮箱管理。
- 邮件发送记录和结果查询。
- 授权范围内的收件箱查询和邮件读取。
- 邮件线程及回复关联。
- 邮件群组。
- 邮件与业务编号关联。
- 回执跟踪。

邮件状态必须区分：

| 状态 | 含义 |
| --- | --- |
| SUBMITTED | 网关提交成功 |
| ACCEPTED | 邮件服务接受请求 |
| DELIVERED | 获得收件服务器投递确认 |
| READ_CONFIRMED | 获得真实阅读证据 |
| ACKNOWLEDGED | 收件人主动确认 |

不同邮件服务商支持的状态并不一致。网关应声明每个适配器的实际能力，不能承诺所有服务商都支持投递回执或已读回执。

对于必须确认的邮件，可以通过企微卡片或受保护的确认链接收集主动确认。该确认属于业务交互事实，不等同于邮件客户端的已读状态。

### 3.3 临时群聊服务

只提供业务触发的临时群能力，不提供固定部门群管理。

功能范围：

- 创建临时群。
- 设置群名称和群主。
- 添加、移除群成员。
- 修改群名称。
- 查询群信息和成员。
- 向群发送消息。
- 关联业务系统和业务编号。
- 关闭临时群的业务生命周期。
- 查询群创建及操作记录。

业务规则：

1. 每个临时群必须关联调用方和业务事项。
2. 创建时必须明确群主和初始成员。
3. 业务系统不能通过网关操作任意企业微信群。
4. 成员变更必须通过调用方权限和资源权限校验。
5. 创建成功后保存企业微信返回的群标识。
6. 重复创建请求必须支持幂等处理。
7. 业务事项结束时，停止自动发送和自动管理，并保留群资源历史。

**逻辑关闭与物理解散必须分开。** 当前设计不承诺通用的主动解散接口。只有在实际接口和权限验证确认支持时，才增加物理解散能力；不能将停止管理或移除成员描述为已经解散群聊。

### 3.4 视频会议服务

功能范围：

- 创建即时或预约会议（分别验证服务端 API 与客户端唤起能力）。
- 修改预约会议。
- 取消会议。
- 查询会议详情。
- 管理参会人员。
- 获取参会入口。
- 查询可获得的参会状态。
- 发送会议邀请。
- 会议与业务事项关联。

业务规则：

- 会议必须关联调用方和业务编号。
- 组织者及参会人员必须通过内部身份映射和范围校验。
- 只能修改、取消网关有权限管理的会议。
- 创建会议成功不代表所有参会人已收到邀请。
- 会议实际参与状态以会议服务提供的数据为准。
- 会议结束不代表业务事项自动结束。

### 3.5 日程服务

日程与会议分开建模，支持：

- 创建、修改和删除日程。
- 添加、移除参与人。
- 查询日程和日历。
- 发送日程邀请。
- 查询成员忙闲信息（以实际授权和接口能力为准）。
- 日程关联会议及业务事项。

通过应用创建的日历和日程，应遵守企业微信实际的应用隔离和资源权限规则，不能假设其他应用可以直接管理。

### 3.6 待办服务

产品决策是优先使用企业微信原生待办，但必须先验证自建应用是否具有适用的服务端 API。

目标能力：

- 创建待办。
- 指定负责人。
- 设置截止时间。
- 修改和取消待办。
- 查询待办。
- 完成待办。
- 获取状态变化。
- 关联业务事项。

上述能力在接口验证前均不能视为已具备。企业微信客户端存在待办功能，不代表自建应用拥有完整 CRUD 和状态回调 API。待办模块应设计为可插拔适配器，验证通过后再确定可承诺的功能范围。

### 3.7 文档与表格服务

采用统一业务接口，分别适配企业微信智能表格和内部表格。

目标能力：

- 创建表格。
- 查询表格、数据表和字段。
- 创建、修改、删除字段。
- 新增、读取、修改、删除记录。
- 批量写入。
- 条件查询和分页查询。
- 视图管理（按渠道能力）。
- 设置和查询资源权限。
- 记录操作审计。

两类表格定位不同：

| 企业微信智能表格 | 内部表格 |
| --- | --- |
| 面向员工协作和可视化 | 面向业务系统数据处理 |
| 支持多人客户端编辑 | 由内部系统控制 |
| 适合收集和人工维护 | 适合结构化查询和程序化操作 |
| 使用平台自身字段、视图模型 | 使用内部数据模型和事务规则 |

统一 API 不意味着强制两种表格使用完全相同的数据模型。智能表格的公式、视图和字段类型未必能映射为内部数据库字段。

内部表格写操作必须包含字段白名单、权限校验、数据校验、版本控制和审计；读取操作必须有资源范围约束和敏感字段保护。

### 3.8 组织与身份服务

- 查询员工和部门。
- 查询部门成员。
- 查询员工状态和所属部门。
- 维护内部用户 ID 与企业微信 userid 的映射。
- 接收通讯录变更。
- 查询调用方可访问的人员范围。

内部统一用户 ID 是业务主键，企业微信 userid 是外部渠道标识。业务系统不应直接依赖企业微信原始标识作为自身主键。

### 3.9 文件服务

后续扩展：

- 上传、下载和查询文件元信息。
- 发送文件。
- 文件与消息、会议、表格关联。
- 文件权限校验。
- 文件过期和归档。

企业微信临时素材、微盘文件和内部对象存储属于不同资源体系，不能把临时素材 ID 当作永久文件标识。

## 四、统一 API 契约

建议采用 REST API，按资源划分：

| API 前缀 | 能力 |
| --- | --- |
| /api/v1/messages | 消息 |
| /api/v1/notifications | 通知及确认 |
| /api/v1/emails | 邮件 |
| /api/v1/chat-groups | 临时群 |
| /api/v1/meetings | 会议 |
| /api/v1/calendars | 日程 |
| /api/v1/todos | 待办 |
| /api/v1/tables | 表格 |
| /api/v1/files | 文件 |
| /api/v1/users | 用户 |
| /api/v1/departments | 部门 |

### 4.1 请求示例

请求示意：

~~~http
POST /api/v1/notifications
Authorization: Bearer <access_token>
Idempotency-Key: incident-001-notify-001
Content-Type: application/json
~~~

~~~json
{
  "source": {
    "system": "incident-center",
    "businessId": "INC20261119001",
    "businessType": "incident"
  },
  "channel": ["wecom"],
  "recipients": [
    { "type": "user", "id": "user-001" },
    { "type": "chat_group", "id": "group-001" }
  ],
  "message": {
    "template": "incident-critical",
    "variables": {
      "title": "支付系统异常",
      "severity": "critical"
    }
  },
  "policy": {
    "level": "L3",
    "requireAcknowledgement": true,
    "acknowledgementRule": "ANY",
    "deadline": "2026-11-19T15:00:00+08:00"
  }
}
~~~

响应中的 ACCEPTED 只表示网关接受请求，不表示消息已送达。

### 4.2 统一执行状态

| 状态 | 含义 |
| --- | --- |
| ACCEPTED | 网关已接受 |
| PROCESSING | 正在执行 |
| SUCCEEDED | 渠道执行成功 |
| PARTIAL_SUCCEEDED | 部分对象成功 |
| FAILED | 执行失败 |
| UNKNOWN | 执行结果无法确认 |
| CANCELLED | 已取消 |
| EXPIRED | 已过期 |

UNKNOWN 是必要状态：例如外部接口调用后网络超时，不能直接判定失败并重发。应先通过可用的查询、回调或对账机制核对，避免重复创建资源或重复发送。

### 4.3 统一回调协议

回调事件至少包含：

- 唯一 eventId。
- eventType。
- requestId。
- 调用方及业务编号。
- 操作人内部用户 ID。
- 发生时间。
- 事件数据。

回调应具备签名验证、防重放、幂等处理、失败重试和事件查询能力。建议采用至少一次投递语义，由接收方按 eventId 去重；不承诺网络环境下绝对不重复投递。

## 五、统一业务规则

1. **业务归属**：每个外部资源操作都必须关联调用方和业务来源。
2. **身份映射**：用户操作必须解析为可信的内部用户身份，不能相信前端自报姓名或 userid。
3. **权限分离**：网关校验通信能力及资源操作权限；业务系统校验用户是否有权执行实际业务动作。
4. **配置快照**：请求接受时固化模板、策略和接收对象，后续配置变化不影响已接受请求。
5. **幂等**：通知、邮件、群、会议、待办、表格创建和记录写入等操作需要幂等控制。
6. **异步执行**：耗时或可能受渠道影响的操作采用异步任务，返回 requestId 供查询。
7. **超时与重试**：网络超时不等于失败；不确定结果进入 UNKNOWN；仅对可安全重试的操作自动重试。
8. **交互事实**：交互事件只记录事实；重复操作不重复产生效果；过期入口不能继续执行有效业务操作。
9. **临时群**：只管理网关创建且已授权的业务临时群，逻辑关闭和物理解散分开。
10. **数据访问**：表格读写按资源授权，支持字段范围、脱敏和批量导出审计。
11. **审计**：记录调用方、操作人、动作、资源、渠道、时间、结果、错误码、重试次数和关联 ID。
12. **渠道隔离**：邮件、企微消息、会议和表格适配器独立配置超时、限流、熔断和重试。
13. **外发内容**：优先采用审核过的固定模板和参数，只发送必要摘要、等级、编号和内部入口，不暴露内部系统敏感详情。

## 六、权限与安全

调用方授权模型：

**Client → Capability → Resource → Action**

例如，故障治理系统可以被授权发送通知、使用特定模板、通知指定人员范围和创建临时群，但这不代表它有权读取所有员工邮箱或管理任意群聊。

权限应细化到：

- 调用方可以使用哪些能力。
- 可以使用哪些渠道。
- 可以通知哪些人员或群。
- 可以使用哪些模板。
- 可以创建哪些资源。
- 可以对哪些资源执行哪些动作。

高风险操作包括移除群成员、外发邮件、读取邮箱、删除表格记录和读取敏感文件，应配置更严格的资源级授权和审计。

凭证安全要求：

- 企业微信 Secret 只保存在服务端密钥管理系统。
- 不向业务系统返回企业微信 access_token。
- 不允许业务系统绕过网关授权直接调用企业微信 API。
- 不同适配器独立管理凭证。
- 支持凭证轮换和审计。
- 回调 URL 应防止 SSRF，并限制访问目标。

## 七、核心数据模型

建议按职责拆分，不把所有能力塞进通用 message 表。

### 7.1 调用方与权限

- ClientSystem：调用方系统。
- ClientCredential：调用凭证及有效期。
- ClientPermission：调用方能力和资源范围。
- UserIdentity：内部用户与外部渠道标识映射。
- Department：组织部门。
- ResourceGrant：调用方对具体资源的授权。

### 7.2 通信请求

- CommunicationRequest：统一请求、调用方、业务编号和执行状态。
- Notification：消息等级及策略快照。
- NotificationRecipient：接收对象、渠道和发送状态。
- Interaction：用户操作类型、操作人和发生时间。
- EmailMessage：邮件渠道、主题和状态。
- DeliveryAttempt：渠道调用、结果、错误和重试次数。

### 7.3 外部资源

- ChatGroup：企业微信群标识、创建方、业务编号和状态。
- Meeting：会议标识、组织者、时间和状态。
- Calendar：日历标识、创建方和状态。
- Todo：外部任务标识及可获得的状态。
- Document / Table：文档或表格提供方、资源类型和标识。
- File：文件位置、存储类型和资源标识。

### 7.4 事件与审计

- OutboxEvent：待发布事件。
- CallbackSubscription：调用方回调配置。
- CallbackDelivery：事件投递记录。
- AuditLog：操作审计。

建议使用 Outbox Pattern，降低数据库事务提交与事件发布之间的不一致风险。

## 八、可靠性与验收

初始容量参考为日均约 100～1000 条通知。该规模用于首期容量规划，不代表最终容量上限。

建议的工程验收目标：

| 维度 | 建议目标 |
| --- | --- |
| 网关 API 可用性 | 月度 99.9% |
| 网关内部请求受理 | P95 ≤ 500ms |
| 普通消息受理至渠道提交 | P95 ≤ 5s |
| 已接受请求持久化 | 不丢失 |
| 回调投递 | 支持重试和补偿 |
| 重复请求 | 幂等控制 |
| 外部渠道异常 | 独立隔离 |
| 操作审计 | 关键操作全覆盖 |
| 异常状态 | 可查询、可追踪 |

这些是建议验收指标，不是企业微信 SLA，也不是未经测试即可承诺的性能。

关键测试场景：

1. 正常发送及批量发送。
2. 接口超时和渠道限流。
3. 同一请求重复提交。
4. 多人同时确认及重复点击。
5. 卡片过期后点击。
6. 用户被移出可见范围。
7. 调用方权限撤销。
8. 邮件服务商不可用。
9. 群创建成功但网关未收到响应。
10. 表格部分批量写入失败。
11. 回调重复投递和乱序。
12. access_token 过期。
13. 网络恢复后的状态核对与补偿。

## 九、建设阶段

### V1.0：通信基础网关

首期重点：

- 调用方注册、认证和授权。
- 组织与身份映射。
- 个人消息、群消息、模板卡片。
- 通知等级、确认和超时提醒。
- 企业微信邮箱及外部邮箱发送。
- 临时群创建和成员管理。
- 回调、幂等、限流、审计、监控和异常跟踪。

首期必须稳定实现的闭环：

**业务系统调用 → 网关通知 → 员工确认 → 网关回调 → 业务系统处理**

### V1.1：协作资源能力

- 会议创建、修改、取消和查询。
- 日程管理。
- 待办（完成原生 API 验证后接入）。
- 企业微信智能表格 CRUD。
- 内部表格 CRUD、查询和权限管理。
- 邮件收件箱、线程和回执能力。
- 文件上传、下载和发送。

### V1.2：治理增强

- 多渠道通知策略。
- 通知统计分析。
- 批量任务调度。
- 统一协作资源查询。
- 会议及待办状态同步。
- 高级表格能力。
- 通信质量监控。
- 资源生命周期治理。

## 十、明确排除的范围

本期不建设：

- 独立工单、故障治理、审批或项目管理系统。
- 独立任务管理系统，任务优先使用企业微信原生待办。
- 固定部门群管理。
- 完整邮件客户端。
- 完整在线文档编辑器。
- 独立视频会议系统。
- 业务人员绩效管理。
- 业务事项最终裁决引擎。
- 未经授权的跨业务系统资源共享。
- 未经接口验证的群聊物理解散和邮件已读回执统一能力。

## 十一、接口能力验证清单

正式承诺功能前，必须针对企业微信实际 API、权限和企业环境完成验证：

| 编号 | 验证项 | 重点 |
| --- | --- | --- |
| V-001 | 自建应用原生待办 | 创建、查询、修改、完成、回调是否完整 |
| V-002 | 企业微信邮件 | 发送、收件箱、邮件读取及回执 |
| V-003 | 临时群 | 创建、成员管理、关闭和解散 |
| V-004 | 视频会议 | 预约、即时会议唤起、参会状态 |
| V-005 | 智能表格 | 字段类型、批量操作和权限边界 |

每项验证应记录官方接口名称、API 地址、权限要求、请求响应结构、可见范围、限流、实际测试结果和不支持场景。

其中待办接口是重要架构决策门槛：客户端有某项功能，不代表自建应用具备对应服务端 API。验证不通过时，应调整功能承诺，而不是假定接口存在。

## 十二、后续设计顺序

1. **领域模型收敛**：确定调用方、通信请求、通知、接收对象、交互和外部资源之间的关系。
2. **API 契约设计**：定义请求、响应、状态码、异步处理和回调。
3. **权限模型设计**：确定调用方能力、人员范围和资源操作授权。
4. **企业微信 API 验证**：重点验证待办、邮件、群聊、会议和智能表格。
5. **技术架构设计**：确定模块边界、数据库、消息队列、适配器和部署方式。

系统的核心价值不在于封装多少个企业微信 API，而在于建立稳定、跨业务系统可复用的通信契约。更换邮箱服务商或增加会议平台时，业务系统不应因此重写业务逻辑。
